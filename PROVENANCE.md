# Provenance and review status

This file states plainly how greengage was built, what has and has not been reviewed, and what you should not yet rely on. It exists because the project asks other people to trust its artifacts; the least it can do is be precise about why, and why not yet.

## Who builds this

greengage is a single-maintainer project (dm0). The specifications, test vectors, and reference implementation are drafted with heavy use of AI coding agents, working under a gated workflow (`AGENTS.md`): every specification and implementation change lands by pull request, and every PR-bearing change ends with an adversarial review pass before a human merges it.

## What the adversarial reviews are, and are not

Each spec and implementation PR is reviewed by a fresh-context, authorship-blind AI agent running a fixed adversarial protocol: removal audits (argue for deleting every protocol element), attack synthesis (construct concrete attacks, report attempted-and-blocked ones), specification-versus-implementation divergence hunting, and prior-art audits. The review memos live on the pull requests in the private development repository, which serves as the provenance archive (the public repository is a scrubbed snapshot with fresh history — procedure in `docs/publication.md`). Memos are available on request, and publishing them alongside the specs is planned.

These reviews are real and they have found real defects. They are **not an independent security audit**. The reviewing agents share a vendor and a broad training lineage with the authoring agents, the protocol has not been reviewed by a named external firm, and no independent team has implemented the specifications from scratch. Treat the whole suite accordingly: suitable for evaluation, prototyping, and integration experiments; not yet suitable as the sole evidence layer for value at risk.

## What would change that status

In order of weight:

1. **A second, independent implementation** of the specs passing the published test vectors. The vectors were generated by a Python oracle that shares no code with the Rust implementation, so they can adjudicate between implementations — but the oracle shares authorship with the implementation, so it is an independent *codebase*, not an independent *party*. (One known gap: the oracle's RFC 6962 Merkle functions are hand-rolled rather than cross-checked against an existing 6962 implementation; that cross-check is queued with the vector-coverage work below.)
2. **An external audit** of the specification suite and the reference verifier by a named firm.
3. **Production exposure** through integrations where greengage artifacts are one evidence layer among several, so a defect is survivable and observable.

## Known open items

Frozen does not mean beyond question. Open items against frozen text are tracked rather than silently patched. Two are currently open (from the Epic 3 adversarial review):

- **Witnessed-log vector geometry (§6.3)**: the current conformance vectors exercise a limited set of tree shapes; broader geometry coverage is queued.
- **§6.3.2 wording**: equal-size and empty-old consistency checks require an empty proof; the normative text says this less directly than it should.

Neither changes verifier behavior as vectored; both are wording/coverage improvements queued for the next protocol epic.

## Design authority

The specifications consolidate a private research corpus (the "S1 programme" in the sibling `damson` research repository), which is not published. What is published carries its own justification: every locked decision in `IMPLEMENTATION_PLAN.md` §2 has a one-line rationale, and every protocol element in the specs has a removal-table row naming the concrete attack its removal enables. Where a rationale cites a corpus document (the `P*` references), the corpus is the historical record of how the decision was reached, not additional normative content; the specs are self-contained.

## Cryptography

greengage invents no cryptography. It profiles standard constructions and uses them as black boxes: COSE_Sign / COSE_Sign1 (RFC 9052) over deterministic CBOR (RFC 8949 §4.2.1), Ed25519 and ES256K signatures, and RFC 6962 Merkle-tree inclusion and consistency proofs. The deterministic-CBOR encoder in `bcf-core` is hand-rolled for byte-level control and re-encode-and-compare canonicality checking; it is small and written to be read, and it is exactly the kind of component an external audit should look at first.
